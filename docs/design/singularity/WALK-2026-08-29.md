## 1. The Agents rail paints `Working` over a seat nobody is answering for

- **What I did.** Seeded this umbrella's real events (incl. the three real
  kind-24223 leases), opened the umbrella, clicked the header chip →
  *Agent details* to open the Agents rail. Ran twice: once with leases inside
  their freshness window (`R3-agents-rail.png`), once **2m02s** later with the
  same leases now stale (`S-R3-agents-rail.png`). The strip's own relative clock
  corroborates the gap — the poker seat reads `last turn 6m ago` in the first
  frame and `8m ago` in the second.
- **What the screen said.** In the stale-lease frame, for **one** execution
  (`9796af42·poker`), four surfaces at once:
  - disposition strip: `Poker · no provider answering · last turn 8m ago`
  - header chip: `3 agents · 3 need attention`
  - Agents rail row: `Poker` / `Claude · opus · 1M` / **`Working`** (in blue)
  - rail footer: **`1 working`**

  and for Lead and Designer, strip `no provider answering` against rail `Idle`.
  Captures: `S-R3-agents-rail.png`, `S-R7-provenance.png` (same frame, popover
  open), `S-R10-whole-window.png`.
- **What the wire says.** The 44223 status for the poker seat was `running`; its
  lease had aged out. Per **W1** the honest word is the demoted one — which is
  what the strip and the header chip print. The rail does not demote:
  `CodingSessionExecutionRail.tsx:398` (`executionStatus`) switches on the raw
  44223 string, and `:307-311` (`ExecutionRailFooter`) recounts
  `activeGeneration.status ∈ {running, starting}` for the footer. The strip goes
  through `deriveCodingSessionWorkspaceStatus`
  (`CodingSessionHeader.tsx:593-598`).

  **Measured proof the rail ignores reachability:** the cropped rail from the
  fresh-lease run and from the stale-lease run are **byte-identical** —
  `sha256 e0dd7b233179ce07767643398cfca0646d114221e34d5eadade75155f60973e2` for
  both `test-results/poker-real-umbrella/R4-rail-only.png` renders. The session's
  reachability changed; the rail's pixels did not. (Only one copy is kept on
  disk, as `R4-rail-only.png`, so the capture set has unique hashes.)
- **Spec element.** `D6` (TEAM), and `A3`'s ruling, reading **W1**.
- **Honest or not.** **Dishonest.** Banksy's diagnosis was right and her fix (D6
  deletes `executionStatus` and threads the demoted resolver in, footer included)
  is the right one; her direction was the mild case. The live case is worse:
  the rail says `Working`, in blue, over a provider nobody is answering for.

## 2. The same fact, four words — and the signed word appears nowhere

- **What I did.** Ran the shipped
  `coding-session-surface-host-screenshots` spec unmodified and read one frame.
- **What the screen said** (`09-ultrawide-agents.png`, also `03-agents-open.png`),
  all for the execution `Claude Code · sonnet`:
  - strip: `Claude Code · sonnet · live · last turn just now`
  - header chip: `2 agents · 1 working`
  - Agents rail: `Idle`
  - rail footer: `All idle`
  - active-work dock: `Active work  1 agent` with that seat's plan at `1/3`
- **What the wire says.** That execution's signed 44223 `status` is
  **`completed`** (`tests/e2e/coding-session-surface-host-screenshots.spec.ts:82`).
  `codingSessionWireWorkspaceStatus` maps `completed` → `{kind: "idle"}`
  (`codingSessionWorkspaceModel.ts:208`), so the rail and footer are the ones
  reading the signed fact. The strip and header get `working` from
  `deriveCodingSessionWorkspaceStatus`'s transcript override
  (`codingSessionWorkspaceModel.ts:360-377`): if the newest transcript item is
  not a turn terminator and its `turnId` differs from the last terminator's, the
  signed status is discarded. `codingSessionDispositionWord`
  (`codingSessionUmbrellaModel.ts:592-594`) then renders that inference as the
  word **`live`** — a reachability word for an activity guess.
- **Spec element.** `W1`, `A3`, `B1` line 2, `D6`.
- **Honest or not.** **Dishonest**, and it is the shape a killed seat leaves
  behind: a provider that dies mid-turn publishes no terminator, so its last
  signed status is a resting one and its transcript looks open. This surface
  answers that with `live` in one place and `All idle` in another, and never
  once with what the provider actually said. **A correction for the spec:** §15(b)
  attributes the split to the rail alone reading raw status. It is a split
  between *two models*, and D6 as written would move every surface onto the
  transcript-override side — i.e. onto `live` for a `completed` execution. The
  override at `:360-377` needs a ruling too, not just the rail.

  |---|---|---|

  | …`toolName` | `Edit` 14 · `Preparing file…` 2 | `Edit` 15 · `Preparing file…` 4 |
  | `tool_result` carrying any `toolKind` | **0 of 187** | **0 of 238** |

  My snapshot's 188 `tool_call`s split `execute` 136, `read` 34, `edit` 16,
  `other` 2. **Not one edit call in either count carries a path, a location or a
  diff** — the payload is always empty; only the tool's *name* is sometimes real.
  So `deriveCodingSessionChangedFiles` has observed edits and nothing to name.
- **Spec element.** **W11**, `A4`, `D3`, `D4`.
- **Honest or not.** **Dishonest.** Every observed edit in the session rendered

## 6. The push error blames a missing repository for an authorization refusal

- **What I did**, on my own key, in my own worktree:

  ```
  git push origin HEAD:refs/heads/poke/texas-throwaway
  bee git check
  ```
- **What the screen said.**

  ```
  remote: repository not found
  fatal: repository 'https://hive.agiterra.org/git/6cbdf445…/agiterra-beekeeper/' not found
  ```

  against

  ```
  relay   https://hive.agiterra.org
  key     9796af42…9bf8  (from NOSTR_PRIVATE_KEY)
  member  NO — the relay rejects this key: restricted: not a relay member
  ```
- **What the wire says.** With `GIT_CURL_VERBOSE=1` the push sends
  `Authorization: Nostr …` and the relay answers **HTTP 404**, 20 bytes,
  `repository not found`. This is deliberate: `authorize_git_read`
  (`crates/beekeeper-relay/src/api/git/transport.rs:502-511`) returns the same generic
  404 for every denial *"so membership cannot be probed through the git
  endpoints"*, and the tests pin it (`:3259 GENERIC_DENIAL`). The 403
  `restricted: not a relay member` at `:240` never fires for this path.
  **Refinement on the brief:** it is not a masked 401 by git — the relay itself
  chooses 404 over 403, on purpose.
- **Spec element.** `unspecified` — no element in §§3–10 covers the seat's git
  path.
- **Honest or not.** **Dishonest at the point of use, by a defensible design.**
  The anti-enumeration property is worth keeping; what is not defensible is that
  nothing points the seat at `bee git check`, which names the real cause in one
  line. A hired seat hits this on its first push, every time.

### 6a. `bee git status` names a key the helper will never use

- **What I did.** `bee git status` in the same shell as the failing push.
- **What the screen said.** `"keyfile": "/Users/brian/.nostr/key"`,
  `"keyfile_pubkey": "3d3b7169…c05e"`, `"configured": true`,
  `"next": "run \`bee git check\` to confirm the relay accepts this key"` —
  "this key" being Brian's.
- **What the wire says.** `git-credential-nostr` prefers the environment:
  `if let Ok(val) = std::env::var("NOSTR_PRIVATE_KEY")` at
  `crates/git-credential-nostr/src/lib.rs:51`, and only falls back to
  `nostr.keyfile` at `:56`. Every hired seat runs with `NOSTR_PRIVATE_KEY`
  injected, so the keyfile key is *never* the one git uses.
  `bee git check` agrees — it reports `9796af42… (from NOSTR_PRIVATE_KEY)`.
- **Spec element.** `unspecified`.
- **Honest or not.** **Dishonest.** Two commands, one shell, two different
  identities, no disclosure in either. `bee git status` should say which key
  will actually be used, or say that the environment overrides the keyfile.

## 7. Controls I could not test without firing them

`Stop all`, `Close session`, `Reopen`, `Export transcript`, interrupt and steer
are all **untested-by-fence** — this lane observes, and firing any of them would
have acted on a live session. What firing `Stop all` would prove: whether its
count matches the seats it actually stops, and whether a seat it reports as
stopped reports itself stopped on the wire (`A7`'s verbatim sentence promises
"a stopped seat cannot be resumed"). In this walk the founder-only controls did
not render at all, because the mock viewer holds no authority (§8), so I have no
pixels for `A7`.

## 9. Smaller things, and what surprised me

- **`Session overview · 0 items 0.0s`** renders a literal zero
  (`S-R3-agents-rail.png`, mid-stream). The spec's rule for numbers of this kind
  is "never `0`" (`E2`, `E3`). Cosmetic, one line, listed so it is not lost.
- **The goal line is a count.** No 44227 exists for this sessionRef — I queried
  it: `bee events query --kinds 44227 --channel 15df7e7f…` returns **0 events**.
  The header therefore shows `BanksyTest` over `3 executions` and never says
  `No goal set`. Not a lie; exactly what `A2`/`A5` predicted, confirmed live.
- **The elision disclosure is good and I want to say so.** The lead's opening
  turn renders as `[elided private context: 67 bytes,
  sha256:a39f12250cc25119a084511d4d569ae1eb8a60f310da67f442fda1b800fc23cf]`
  inline in the message. That is a surface refusing to show something *and*
  telling you exactly how much it withheld and how to verify it. It is the best
  honesty behaviour I saw all walk.
- **What surprised me most:** the client verifies signatures on coding-session
  ingress and drops anything that fails, silently, into `Coding sessions (0)` with
  the copy *"No signed sessions in this channel yet. Sessions started here appear
  in this list as soon as the provider signs its first event."* I spent three
  runs believing my events were malformed. For a person whose provider is
  publishing events with a key the client will not accept, that screen says the
  provider has not started — which is not what happened. I did not chase it far
  enough to call it a finding, but it is the same class, and it is one grep from
  being one: `channelCodingSessionIngress.ts:44`.
- **`bee sessions status` reports my own context as `null`** while the lead's and
  designer's report fine. Whatever emits `context_window_updated` had not fired
  for my execution. Per `W12`/`D7` the honest render is `window unknown`; there
  is no desktop surface reading it yet, so nothing lied — noting it for the lane
  that builds D7.

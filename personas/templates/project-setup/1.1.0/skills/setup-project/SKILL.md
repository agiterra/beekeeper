## Discover the project

Start from the supplied project intent, repository and setup context. Inspect
the relevant instructions, working tree, existing role procedures and supported
tools. Establish the goal, current state, actual build/test workflow, useful
roles, acceptance evidence, standing grants and unresolved questions. Cite the
observations behind project-specific commands. Do not infer procedures from
another project or copy machine credentials.

Inspect tools, commands, configuration and repository state yourself. Ask the
owner only for what inspection cannot establish, and say what you checked.

## Reconcile existing instructions

Existing contributor and agent instructions are project policy to reconcile,
not text to copy or discard. Identify where they conflict with a
lead-coordinated team whose lead picks workers by task, such as a fixed roster,
a mandatory participant or a staffing sequence. Ordinary solo sessions remain
a supported way to work; do not make a team, a role or a reviewer count a
prerequisite the instructions do not state.

Preserve every product, security, testing and independent review requirement.
Where a requirement names a specific agent, reviewer, tool, budget, model or
staffing arrangement, record the underlying requirement, map it to an available
role where the mapping is clear, and list the name or assumption for the owner
to reconcile instead of making it a role dependency. An unavailable named
reviewer never removes the independent review it stood for.

If instructions are generated from a source file by a generator, never edit
the generated output; name the source and generator in the report and propose
changes there. Never silently rewrite project policy files or drop an
independent review requirement. Report each item for reconciliation with its
source, the underlying requirement, the proposed role mapping and the name or
assumption to confirm.

## Prepare project-owned procedures

Use the assigned role-pack workspace and its saved project source. For a new
source, adapt the neutral baseline supplied by the host. For an existing source,
edit its current project-owned copies and preserve unrelated customizations;
never reset them to a newer shipped baseline. Record the starting source and
revision. Keep procedures concise, with clear responsibilities, boundaries,
acceptance evidence and handover behavior. Validate the pack manifests, persona
and skill references, then exercise the applicable project checks.

Save only within the assigned workspace. A role pack does not confer authority:
do not impersonate the owner, alter credentials, change unrelated project
records or publish through an ambient key. One subscription must suffice for
ordinary work. Document unknowns and unmet grants honestly while completing the
parts already authorized.

## Demonstrate readiness

Readiness is something you **exercised**, not something you wrote down. A
procedure you have not run is a proposal; say so in those words.

Before reporting, run what you are claiming: the project's build, test and
check commands you recorded, from the directory a worker will actually stand
in; the resolution of every role, template and skill reference you prepared;
any routing or registry lookup a hire will depend on; and at least one end of
each capability the team will need. For each, report the exact command, where
it ran, its exit status and the observable counts or output.

Name the precise missing grants the same way: the operation refused, the
authority it required, who can supply it, and what the team can still do
without it. "Not yet authorized" with the exact capability named is a useful
result; a confident readiness claim over an unrun command is a defect.

## Submit through the task's capability

When the host supplies a scoped publication capability, use its documented
interface to submit the prepared workspace for this project and expected source
revision. The host checks the grant and current state. Do not invent a CLI
command or assume an unseated session can publish as the owner. If no such
capability is available, retain the prepared changes and report the exact missing
capability through the task's reporting surface.

Read the submission result. On a conflicting source revision, inspect the new
project changes and reconcile without overwriting them. On failure, report the
actual condition; do not say the setup was saved. On success, report the
published source and revision, checks performed, items left for the owner to
reconcile and remaining setup needs.
Publication, staging and observed execution are separate facts. New work should
resolve the project's current published copy; an active execution keeps the
instructions it staged. Never claim adoption from publication alone.
